## 1. 这一轮做了什么

一句话：**把「能连上」变成「一个不懂网络的人也能连上，而且出问题知道怎么办」。**

三条主线：

1. **联机流程产品化**：建房页直接给出「发给室友的地址」；加入页有房间卡片、支持粘贴
   `192.168.1.5:28080`；多网卡时明确区分「推荐地址 / 备选地址 / 已忽略的虚拟网卡」。
2. **诊断能力**：把「连不上」拆成 10 种可行动的结论（内置连接测试），
   并支持导出脱敏诊断包。
3. **多人局节奏与状态**：新增聚会模式（5～6 人 45～50 分钟）、AI 演出速度、
   大厅状态机、掉线/重连体验、破产演出、结算时间线、本局记录、新手引导。

## 2. 玩家视角最重要的变化

| 以前 | 现在 |
| --- | --- |
| 建房页没有 IP，得先建房再进大厅找 | 建房页直接显示「这台电脑的局域网地址」，多网卡时给推荐 + 备选 |

| 连不上只显示「连接失败」 | 诊断页分类：拒绝连接 / 超时 / 网络不可达 / 版本不一致 / 房间已满 / 已开局 / 协议错误 / 未知 |

| 第一次进对局没人管 | 6 步引导，高亮真实控件，可跳过、可「不再显示」、设置里可重开 |

## 3. LAN 建房流程

```
主菜单 →「局域网联机」（展开）→ 创建房间
  ├─ 昵称 / 房间名称 / 端口
  ├─ 右侧「这台电脑的局域网地址」
  │    · 推荐地址（大字）：192.168.1.103（WLAN）
  │    · 一句人话结论：标准的家用 / 校园局域网地址，适合发给室友
  │    · 备选地址：169.254.x.x（以太网）  ← 有多个网卡时
  │    · 已忽略虚拟网卡（室友连不上）：本地连接* 1、本地连接* 2
  │    · 「复制连接信息」按钮
  └─ 三步说明：创建房间 → 复制连接信息 → 室友粘贴加入
```

点「创建房间」后进入大厅，大厅顶部有一个**加粗大字地址**：

```
把下面这一行发给室友（同一个 WiFi 下就能加入）
192.168.1.103:28080              WLAN
其它可用地址：…（多个网卡时）
[复制连接信息]
```

「复制连接信息」写进剪贴板的内容（多行带标签，粘到群里别人也看得懂）：

```
Richman v0.4.0-rc1
房间：321 宿舍局
IP：192.168.1.103
端口：28080
版本：0.4.0-rc1
```

## 4. 加入房间流程

```
主菜单 →「局域网联机」→ 加入房间
  ├─ 昵称 / 房主发来的地址（IP，可以带端口）/ 端口
  └─ 右侧「自动发现的房间」（每 1.5 秒刷新）
       321 宿舍局   192.168.1.23:28080  房主 阿明  2/6 人  城市之光   [可加入]
       老张的房间   192.168.1.31:28080  房主 老张  6/6 人  海滨假日   [已满]
       版本不一致的… 192.168.1.44:28080  房主 小李  1/6 人  城市之光   [版本不一致]
```

- **点整张卡片即可加入**（无需先选中再确认）
- 卡片上直接显示版本是否兼容 —— 版本不一致时不会等 TCP 报错才知道
- 空态不是干等：说明「会自动刷新 / 校园网可能屏蔽广播 / 请让房主复制地址给你」
- 手动输入支持：`192.168.1.10`、`192.168.1.10:28080`、`192.168.1.10：28080`、
  `http://192.168.1.10:28080`、带引号的粘贴内容

## 5. 多网卡问题

以前：`socket.gethostname()` + `getaddrinfo` 返回裸 IP 列表，随便取第一个，
**可能是 VirtualBox / 蓝牙 / WSL 的地址**，发给室友必然连不上。

现在（`src/network/netinfo.py`）：

- 用 Windows 自带的 `iphlpapi.GetAdaptersAddresses`（ctypes 直接调用，不依赖第三方库，
  打包后同样可用）拿到网卡**名称、描述、类型、状态**
- 按「室友能不能访问到」排序：**通的网卡 > 私有网段 > 类型（有线 > 无线 > 其它 > 虚拟 > 回环）**
- 判定虚拟网卡看名字特征（VirtualBox / VMware / Hyper-V / Bluetooth / VPN / WSL…），
  比只看 `IF_TYPE` 可靠 —— 因为虚拟网卡的 IF_TYPE 也是「以太网」
- 诊断页按当前状态给结论：
  - `127.0.0.1` → 「这个地址只能本机访问，**请不要发给室友**」（danger）
  - `169.254.x.x` → 「当前可能没有正常获得局域网地址（DHCP 失败）」（danger）
  - 多个物理网卡 → 「如果室友用第一个地址连不上，请把「其它地址」也发给他试一次」
  - 虚拟网卡 → 折叠成一行「已忽略虚拟网卡（室友连不上）」

本机实测（真实枚举结果）：

```
up=True  192.168.1.103  wifi     WLAN / Intel(R) Wi-Fi 6E AX211      ← 推荐
up=False 169.254.146.6  ethernet 以太网 / Realtek Gaming GbE         ← 备选（未连接）
up=False 169.254.195.222 virtual 本地连接* 1 / Wi-Fi Direct Virtual Adapter
up=False 169.254.173.47  virtual 蓝牙网络连接 / Bluetooth Device PAN
        127.0.0.1        loopback Loopback Pseudo-Interface 1
```

## 6. 联机诊断能检测什么

`主菜单 → 局域网联机 → 联机诊断`，每 2.5 秒自检一次：

| 项目 | 数据来源 | 诚实性 |
| --- | --- | --- |
| 游戏版本 | `version.py` | 真实 |
| 当前网络 | 网卡类型归类（Wi-Fi / 以太网 / 两者 / 仅虚拟） | 真实 |
| 推荐地址 + 人话结论 | 网卡枚举 + 地址段判断 | 真实 |
| 备选地址 / 已忽略虚拟网卡 | 同上 | 真实 |
| 服务端端口 | 房主：实际监听端口；未建房：试绑默认端口 | 真实 |
| 房间自动发现（UDP） | 试绑 28081 | 真实（并说明「本机能收广播 ≠ 一定能收到」） |
| 最近一次连接 | 房主侧 join/probe 结果；客户端侧测试结果 | 真实 |
| 下一步怎么办 | 按上面结果动态生成（不是固定清单） | — |

**明确不做的**：不声称「Windows 防火墙已放行」。页面底部写着：

> 说明：本页不会假装检测防火墙——那需要管理员权限，检测不出来就不给结论。

## 7. 不能可靠检测的网络问题

诚实清单（都在页面上或报告里写明）：

1. **Windows 防火墙是否放行本程序** —— 需要管理员权限与平台 API，
   测不了就不给结论，只给「怎么手动放行」。
2. **路由器 / 校园网是否启用 AP 隔离** —— 这是链路层行为。
   我们只能观察到「TCP 超时」，并把它列为超时的常见原因之一。
3. **UDP 广播是否被网络屏蔽** —— 本机可以绑上 28081（说明自己能收），
   但收不到房间广播可能是网络屏蔽。页面明确说「搜不到请让房主复制地址」。
4. **对方的网络环境** —— 只能看到对方的 IP 与版本，看不到它的网卡与防火墙。

## 8. 一键连接测试

诊断页 →「测试连接」：输入 `IP` 或 `IP:端口` → 真的建 TCP 连接 + 一次轻量握手。

支持的结果分类（不是「连接失败」四个字）：

| 结果 | 触发条件 | 给玩家的动作 |
| --- | --- | --- |
| **连接成功** | 握手返回 PROBE_RESULT 且房间可加入 | 「可以放心加入这个房间了」 |
| **对方拒绝连接** | `ECONNREFUSED` | 房主没开房间 / 端口填错 |
| **连接超时** | `ETIMEDOUT` | 5 条检查：同 WiFi / 房主还开着 / IP 对 / 防火墙 / AP 隔离 |
| **网络不可达** | `EHOSTUNREACH` / `ENETUNREACH` | 不在同一网段，让两边都对 ipconfig |
| **地址无法解析** | `gaierror` | 只支持 IP，不支持主机名 |
| **版本不一致** | 握手返回 VERSION_MISMATCH | 两台电脑用同一份游戏文件 |
| **房间已满** | PROBE_RESULT `players >= max` | 等下一局 |
| **游戏已开始** | PROBE_RESULT `phase != lobby` | 等他们打完 |
| **协议错误** | 端口通了但不是 Richman | 端口被别的程序占用 |
| **未知错误** | 其它 | 导出诊断包 |

测试用 `PROBE` 消息，**不占座位、不改房间状态**（测试别人的房间不会留下幽灵玩家）。

## 10. 掉线与被重连的玩家体验

掉线方（客户端）：

- **不踢回主菜单**。显示半透明覆盖层（能看见底下的棋盘，知道这一局还在）
- 文案：「与房主连接中断」+ 具体原因 + 「正在尝试重新连接…」
  + 「已等待 N 秒」+ 「**第 2/50 次尝试**」+ 进度条
- 按钮：【立即重试】【返回主菜单】
- 超过 30 秒后提示变成：「已经超过 30 秒，你的座位现在由 AI 临时接管；
  本局不会中断 —— 继续等，连上后会自动把控制权交还给你。」
- 连回来：屏幕中央显示 **「已重新连接到房间」**（带「第 N 次尝试成功」），淡入淡出

**这一轮修掉的一个真问题**：v0.3 里客户端重连窗口与房主宽限期都是 30 秒，
意味着玩家回来时客户端已经放弃 —— 「AI 接管后接回控制权」这条路径实际不可达。
现在客户端窗口是 150 秒（50 次尝试），这条路径才真正走得通。

## 11. AI 接管与恢复控制

房主侧（以及所有人看到的横幅）：

- 掉线瞬间：横幅「XX 与房间失去连接（30 秒内可重连）」，玩家卡写「掉线 N 秒」
- 超过 30 秒：横幅「XX 掉线超过 30 秒，由 AI 代为操作（回来可以接回控制权）」，
  卡片写「AI 接管」
- 回来时：横幅「**XX 重新连接成功并恢复控制**」，控制权从 AI 交还本人

**实测证据**（两个独立进程，房主侧记录的状态序列）：

```
ready → ai → ai → disconnected → ai_takeover → idle
                                   ↑ AI 接管      ↑ 回来后交还控制权（idle = 未准备，可再操作）
```

## 12. 聚会模式改了哪些真实参数

`config/default.json` 的 `presets.party`：

| 参数 | 标准局 | 聚会局 | 为什么这么改 |
| --- | --- | --- | --- |
| `starting_money` | 15,000 | **12,000** | 资金少 → 大租金的容错从 3～4 次降到 2～3 次，破产更早来。不降到 8,000 以下是因为那样会「买不起地 → 空转」，反而变长 |
| `pass_start_bonus` | 2,000 | **1,200** | 经过起点是被动输血。压到 1,200 相当于「刚好够付一次小租金」，保留翻盘可能但不养懒人 |
| `max_rounds` | 200 | **80** | 直接决定"没人破产时"的硬上限。实测聚会局大多在第 43～63 轮就分出胜负，80 轮足够而不会无限拖 |
| `starting_cards` | 2 | **3** | 资金紧了，多给一张道具牌，保证玩家仍然"有牌可打"，回合不空转 |
| `shop_base_price` | 1,200 | **900** | 现金少了，商店价格不降就没人买得起，商店格会变成空转 |
| `bonus_pool_base` | 1,500 | **900** | 奖金池是随机大额收入，会延长局面。降低它让比赛收敛更快 |
| `phase_scale` | 1.0 | **0.62** | **纯演出压缩**：掷骰、结算、过场的时长乘 0.62。演出占一局时间的 53%～55%，这是最直接的省时手段，且不改变任何规则结果 |
| `ai_think_sec` | 0.45 | **0.26** | AI 决策本身是毫秒级的，0.45 秒的"思考"是纯等待。6 人局里 × 6 人 × 80 轮 ≈ 4 分钟 |

**没有动的**：基础租金系数、升级费用、地价、税率、看守所规则、地图。
需求里说"不要简单粗暴全部租金 ×2"—— 上面这些参数**一个都没靠加倍租金来实现**。

| 标准 | 4 | 167.0 | 37.4 min | 51.0 min | **71.0 min** | 87 | 3.0 |
| 快速 | 4 | 96.7 | 25.3 min | 35.1 min | **49.3 min** | 68 | 2.0 |
| 标准 | 5 | 159.3 | 42.0 min | 53.3 min | **81.0 min** | 69 | 4.0 |

## 14. 6 人局是否明显缩短

**是。77.8 → 48.6 分钟，缩短约 38%**（全员真人口径，模拟 3 局均值）。

而且破产结构更健康：标准 6 人平均 4.7 人破产（只剩 1 人），
聚会 6 人平均 3.7 人破产 —— 大多局仍然打到分出胜负，不是被轮数上限截断。

## 15. AI 回合等待感

三处改动：

1. **不再靠"停一秒"来让玩家看懂**：AI 决策本身是毫秒级的（`_decide` 是纯规则计算），
   原来固定等 0.45 秒。现在把这段时间与"演出速度"绑定。
2. **AI 动作变成一句话提示**（`PRIORITY_NORMAL` 横幅，0.65～1.25 秒）：
   - 「阿金 购买了「中央大道」¥800」
   - 「老陈 把「湖滨花园」升到 2 级 ¥600」
   - 「娜娜 使用【抢夺卡】目标：阿明」
   自己操作时不会出提示（不刷自己的屏）。
3. **新增设置「AI 演出速度」**：正常 / 快速（1.7x）/ 极速（3.0x）。
   只缩短「等 AI 的观感」与 AI 回合的过场，**决策结果完全相同**。

## 23. reconnect 实测

在双实例测试里真实发生（不是 API 调用）：

1. 客户端 `shutdown(2)` 掉 socket，并把重连目标临时指向 `192.0.2.1`（TEST-NET-1 不可达网段）
   —— 这样"网线拔掉 34 秒"才是真的拔掉，而不是 3 秒就自动重连成功
2. 房主 30 秒后 AI 接管（`presence: disconnected → ai_takeover`）
3. 客户端第 34 秒把地址改回真实地址，下一次自动尝试成功
4. 房主记录 `ai_takeover → idle`（控制权交还）
5. 双方 `canonical_hash` 完全一致

**这一轮由此修掉两个真实问题**：
- 客户端重连窗口=房主宽限期=30 秒 → 「AI 接管后接回」实际不可达 → 客户端窗口改为 150 秒
- 重连尝试同步阻塞主循环最多 5 秒（界面冻结）→ 局域网重连超时降到 1.5 秒

## 25. 性能结果

`tools/perf_check.py --frames 120`（1600×900 逻辑分辨率，离屏口径）：

| 界面 | 优化前 | 优化后 |
| --- | --- | --- |
| 主菜单（含动画装饰） | 13.16 ms | 10.26 ms |
| 单人配置 | 10.58 ms | 4.71 ms |
| 设置 | 9.93 ms | 2.08 ms |
| 建房页 | 9.96 ms | 3.42 ms |
| **联机诊断** | **34.98 ms** ← 超预算 2 倍 | **2.73 ms** |
| 大厅（4 人） | 10.73 ms | 4.39 ms |

| 对局 · 6 人 | 11.14 ms | 6.43 ms |
